# Where harness-adapter research can improve agent-skills

Research conducted November 28, 2026. [Research log and source records](research-log.md) · [Eval rubric challenges](eval-challenges.md)

## Decision

Two targeted additions are worth making. Give executable graders a concrete task-qualification procedure in **agent-evals-and-observability**. Give **ml-engineering** a worked specialization study that tests adapter gains under the actual deployment harness and inference settings. A short link from **harness-engineering** can connect its existing experiment protocol to that study.

For the grader example, use a disposable CSV fixture with a requirement to export all input records and a grader that initially accepts the expected header alone. The reference and an independently prepared implementation that differs in incidental output formatting should pass. An untouched fixture and a result with the correct header and a missing record should fail. Verifier failure to start is an incomplete trial. Replaying the same accepted fixture tests repeatability within that setup. A skill eval should require the proposed control outcomes and evidence identities. Actual execution receipts would establish whether the controls ran.

In the specialization study, keep **grader validity** separate from **training difficulty**. Sample repeated incumbent rollouts in the intended harness and record mixed, uniformly successful, uniformly unsuccessful and unscored groups. For binary correctness rewards, all-zero or all-one groups have no within-group correctness variation. Four or eight attempts in the source describe its screen, and leave uncertainty about the underlying solve probability. Preserve easy and hard cases for broader regression coverage. When training from harness rollouts, preserve the serving engine's actual per-call token IDs, relevant log probabilities and loss masks. Compaction, template rendering and parser transformations can break continuity across calls. [Source records S1 and S4](research-log.md#s1--hugging-face-scale-study)

If a merged artifact is a deployment candidate, evaluate it as its own candidate against both the base and each specialist and use a per-harness regression gate. Near-orthogonal weight updates can still produce uneven task outcomes. This fits inside the specialization example. [Source records S1, S6 and S8](research-log.md#s6--released-model-card)

## Confidence and follow-up questions

Confidence is high in the catalog overlap check and the proposed grader controls. The public results support testing the harness, adapter and inference settings together. Effect sizes, general portability and production savings remain workload-dependent. The article and released model card describe different compaction settings. Resolve the run configuration before reusing their figures as a common comparison. The source experiment used one base model and one attempt per final benchmark task. Its business-workflow test changed both the harness and the task domain. No benchmark, retraining or production trial was run during this review.

A local study would need to establish whether the control panel catches grading defects on our own tasks, whether adaptation beats a strong incumbent after counting all costs, and how sensitive the decision is to a harness or serving revision.
