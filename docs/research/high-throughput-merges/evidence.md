# Research log and source evidence

Research completed and sources accessed 2026-11-28. [Research question, findings, and application](README.md)

## Search history and inclusion

Searched the public web for GitHub's production merge queue, current configuration and Actions behavior, GitLab merge trains, Rust bors and rollups, Shopify's historical queue and recent agent-heavy work, Uber SubmitQueue papers and production follow-ups, and Google's presubmit and large-change practices. Followed Uber's follow-up citations to the original EuroSys design and GitHub's changelog from the preview to general availability. Used product documentation for current behavior and operator reports for historical deployment. Recent Shopify and GitHub publications provide a check against relying exclusively on older monorepo examples.

The search addressed admission, ordering, merged-candidate checks, failure isolation, batching, competing changes, and deployment backpressure. The cases are purposive, with no controlled comparison across teams. Platform support was checked in public documentation. Repository-specific rules, subscription eligibility, and live CI behavior were outside the research question.

## Queue mechanics

- **GitHub merge queue · current first-party documentation · high confidence for documented behavior.** GitHub.com offers native queues for public repositories owned by organizations and for private repositories owned by organizations using GitHub Enterprise Cloud. The queue builds a temporary candidate using the latest target and earlier queue entries. A failed required check or merge conflict may remove the PR and change downstream candidates. FIFO is the default and jumping to the front rebuilds in-progress groups. Build concurrency throttles dispatch. Merge limits group ready landings without coalescing candidate builds. With Only merge non-failing pull requests disabled, a passing later candidate can cover a group containing an earlier failing candidate. This distinguishes evidence for the final group from evidence for each intermediate state. [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- **GitHub required checks · current first-party documentation · high confidence for documented behavior.** Required Actions workflows need a separate merge_group trigger. Queue and PR candidates have different revisions. Workflow-level filtering can leave required checks pending, while a skipped job can report success. A required aggregator should account for failure, cancellation and expected job execution explicitly. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group) · [Troubleshooting required checks](https://docs.github.com/en/enterprise-cloud@latest/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- **GitLab merge trains · current first-party documentation · high confidence for documented behavior.** Shows the A/B/C parallel-prefix example and cancellation of downstream pipelines after removal. Its immediate-merge option without a restart is documented as experimental and risks retaining checks that omit the newly landed change. The brief uses the protected train path as its default. [Merge trains](https://docs.gitlab.com/ci/pipelines/merge_trains/)
- **Rust bors · project design and compiler developer guide · high confidence for documented design.** Bors combines a PR with the latest target, runs one auto build at a time, and fast-forwards to the passing integration commit. Rust uses selected rollups to amortize its expensive full CI over several PRs. Together these are evidence for serial validation with optional true batching, distinct from a speculative train. [Bors design](https://github.com/rust-lang/bors/blob/main/docs/design.md) · [Rust compiler CI](https://rustc-dev-guide.rust-lang.org/tests/ci.html)

## Engineering case studies

- **GitHub · March 2024 operator case study · high confidence for reported workflow, moderate for attribution.** The old deployment trains relied on a conductor and large groups could derail or take hours. GitHub moved its monorepo and production-service repositories over in phases. It combines and tests candidate changes, ejects conflicts, and reforms deployment groups. It reported about 2,500 merged PRs per month in the large monorepo and a 33% reduction in average wait to ship. Its historical workflow deployed before merging, so the shipping metric includes that path and cannot stand in for queue latency elsewhere. [How GitHub uses merge queue](https://github.blog/engineering/engineering-principles/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/)
- **Shopify · November 2019 operator case study · high confidence for reported design, moderate for outcomes.** Its first Shipit queue limited drift between main and production but did not test queued integration candidates. Its second version checked branch CI and review at admission, reconciled speculative commits on a predictive branch, and discarded obsolete candidates. It identified semantic interactions between individually green changes. Shopify's historical heuristic tolerated successive failures because it expected real failures to persist and flakes to disappear. Correlated failures and changes that fix or mask earlier failures limit that heuristic. The brief uses the stricter per-candidate default and does not carry over Shopify's historical emergency bypass. The account reports roughly 400 **commits** to trunk per day, a different unit from GitHub's PRs per month. [Successfully merging the work of 1,000+ developers](https://shopify.engineering/successfully-merging-work-1000-developers)
- **Uber · EuroSys 2019 operator-authored paper · high confidence for design and bounded empirical findings.** SubmitQueue models build interactions and speculates about possible predecessor outcomes while maintaining serializable landing. Build steps and affected targets can reveal interactions that file overlap misses. Its retrospective Android/iOS figures show more real interactions among larger sets of potentially conflicting changes. Its experiments compare serial, batching and speculation under Uber's workload and resource assumptions. They do not establish universal conflict rates. [Keeping Master Green at Scale, publisher record](https://doi.org/10.1145/3302424.3303970) · [Full paper](https://lethain.com/static/blog/2019/eurosys19uber.pdf)
- **Uber · August 2023 operator follow-up · high confidence for stated rule, moderate for attribution.** To land a small change ahead of an unresolved conflicting change, Uber verified the relevant speculative paths and required consistent results. The Go monorepo's June p95 wait was 74% lower than April's after a late-May rollout. It is a before-and-after comparison. Testing every conflicting path grows exponentially with the number of unresolved conflicting predecessors. [Bypassing Large Diffs in SubmitQueue](https://www.uber.com/rs/en/blog/bypassing-large-diffs-in-submitqueue/)
- **Uber · later operator follow-up · high confidence for described scheduler, moderate for attribution.** Prioritizes speculative builds using estimated likelihood and timing, bounds less useful work, and measures the compute/latency tradeoff. It reports per-monorepo reductions in both CPU hours and p95 waiting time. The measured p95 reductions were about 45% in Go, 33% in iOS, and 32% in Android in that later rollout. These are separate from the 2023 result. Probabilities govern which work the scheduler runs, while actual validation governs landing. [Slashing CI Costs at Uber](https://www.uber.com/de/en/blog/slashing-ci-costs-at-uber/)
- **Google · practitioner book and Google Research · high confidence for historical design.** Google describes fast presubmit subsets, broader batched postsubmit checks, and culprit detection or rollback. This is evidence of a different assurance and latency tradeoff. A fast presubmit suite should have an explicit scope, and broader postsubmit checks need an accountable recovery path. [Continuous Integration](https://abseil.io/resources/swe-book/html/ch23.html) · [What Breaks Google?](https://research.google/pubs/what-breaks-google/)

## Change structure and ownership

- **Google · practitioner book · high confidence for described method.** Large migrations can be divided into independent, reviewable changes. The scoped pointer migration illustrates adapting compatibility while independent changes proceed in parallel. The brief's advice to serialize edits to shared contracts and migrate consumers independently is a synthesis for a PR-based environment. [Large-Scale Changes](https://abseil.io/resources/swe-book/html/ch22.html)
- **GitHub · October 2026 product release · high confidence for documented behavior.** Native stacks provide dependency-ordered, independently reviewable PRs and a stack can enter and land through the queue as a single merge group. GitHub also describes preserving review approvals on an otherwise unchanged stack rebase. Product adoption metrics are excluded from the brief because the comparison design is unspecified. [Stacked pull requests generally available](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/)
- **Shopify · November 2026 operator account · moderate confidence for transfer.** During an agent-heavy native mobile rebuild, engineers reported that CI machines, review, merging, and coordination became bottlenecks. Agents handled branch repair and CI triage. Two-person pods owned app areas to reduce duplicate work. This supports work ownership and integration capacity as first-class concerns. It supplies no controlled measure of the effect of agents or pods on merge performance. [How we rebuilt the Shopify app in 12 weeks](https://shopify.engineering/shopify-app-rebuild)
