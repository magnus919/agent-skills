# Evidence ledger

Sources accessed 2026-11-26. The sponsored video defined the search questions; it was not treated as a controlled comparison. Groktocrawl deep discovery ran separate queries on durable orchestration/integration controls and reviewer effectiveness. It surfaced the author repository and follow-up, GitHub merge-queue guidance, and empirical review literature. Claims below were checked against primary materials; supplemental search covered Git and workflow semantics and closed-loop review benchmarks.

| Source | What it establishes | What it does not establish |
| --- | --- | --- |
| [ZazenCodes v1 video](https://youtu.be/ctoaIC4LHmI?t=1328), [original prompt](https://github.com/zazencodes/zazencodes-season-3/blob/main/src/software-factory-claude-code/BUILD_PROMPT.md), [v1 README](https://github.com/zazencodes/zazencodes-season-3/blob/main/src/software-factory-claude-code/README.md) | Prompt requests one shared board file, role-owned artifacts and bounded rework. Evolved v1 gives jobs separate state and worktrees. The demo shows an approved job failing to merge while the target checkout has a dirty backlog file. | Same source family. Different tasks in the model race; no comparative throughput, cost, or accuracy conclusion. |
| [v2 design](https://github.com/zazencodes/zazencodes-season-3/blob/main/src/software-factory-claude-code-v2/DESIGN.md), [state transition code](https://github.com/zazencodes/zazencodes-season-3/blob/main/src/software-factory-claude-code-v2/factory/bin/job), [gate code](https://github.com/zazencodes/zazencodes-season-3/blob/main/src/software-factory-claude-code-v2/factory/bin/gate) | Source inspection: moves state through a designated writer; adds project checks, protected paths, reviewer routing, PR integration and another gate before merge. The check launcher is taken from the main checkout; it executes inside the candidate worktree. | Not independent validation or a sandbox guarantee. Candidate dependencies and build scripts still matter. Subscription cost estimate is API-equivalent, not the invoice. No evidence that v2 deploys, or that any model or agent count is optimal. |
| [Git worktree documentation](https://git-scm.com/docs/git-worktree), disposable Git fixture | Linked worktrees have separate checkouts, but share most refs and default config. Fixture: two checkouts, job commits a tracked queue file, target holds a local edit to that path; fast-forward fails and preserves the uncommitted data. This verifies an overlapping-edit mechanism, not the demo implementation's exact preflight behavior. | Worktrees are not a security boundary and do not isolate shared ports, external data, or deployment. |
| [GitHub merge-queue docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) | Protected integration can run required checks on a temporary group formed from the latest base and earlier queued changes. Failed checks and conflicts can remove a candidate. | Does not show every repository needs GitHub, a merge queue, or this service tier. A serialized integration lane can enforce the same revision check. |
| [Temporal durable-execution docs](https://docs.temporal.io/durable-execution) | Durable event history preserves completed step results across a process failure; retry and timeout policy handle incomplete work separately. | Does not mean a side effect is exactly once or that a JSON status file alone is crash-safe. Reconcile ambiguous external outcomes before retry. |
| [SWE-Review, July 2026 preprint](https://arxiv.org/html/2607.06065v1) | On the authors' issue-resolution benchmark, review with structured diagnosis and revision can improve executable task outcomes over initial patches; the experiments compare downstream repair, not just review verdict. | Benchmark and selected agent configurations do not determine how many lanes a real repo should use or supply release authorization. |
| [CodeRabbit field analysis, July 2026 preprint](https://arxiv.org/abs/2607.03316v2) | Across 31,073 review/developer-feedback pairs, 36.4% were accepted, 7.3% discussed, 56.3% rejected. Noise included redundant, invalid and out-of-scope suggestions. | Selected feedback pairs on one product, not intrinsic correctness, all emitted comments, or a randomized comparison of review designs. |
| [CR-Bench-v2, November 2026 preprint](https://arxiv.org/abs/2611.02566v2) | Separates detection of known defects from comment usefulness; strongest tested systems find about one-third of labeled defects on this corpus. | Selected historical defects and model-judged evaluation do not give universal recall or make silence evidence of correctness. |

**Excluded or deferred:** product roundups, mirrors and reposted summaries do not add independent evidence; issue discussions aid discovery, not validation. The source family's budget and model claims were not adopted. No matched field study surfaced that establishes one versus four reviewers, which specialties should always run, or a portable savings estimate. The disposable Git fixture tests the integration mechanism only; no product pilot was run.
