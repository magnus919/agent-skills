# Consumer review contract: customer events and export

The contract should let a consumer resolve the intended customer, read a complete event set, and obtain an export without guessing about identity, pagination, permissions, or asynchronous effects. Before implementation, the API owner must define the authoritative customer identifier, event ordering and retention semantics, export data scope, and the authority required to create and retrieve an export. These are domain decisions; if unresolved, the consumer must stop and surface the ambiguity rather than pick a likely customer.

**Customer resolution.** Accept a query as a display name, but return zero, one, or multiple explicit candidate records with stable opaque customer IDs and only permitted disambiguating attributes. Do not make the first match implicitly authoritative. Require the consumer or user to select an ID when more than one candidate exists. Define normalization, locale/case behavior, pagination/limits for candidates, and denied versus not-found responses so the consumer can avoid leaking existence across authorization boundaries. Acceptance evidence: unique name resolves to the expected stable ID; ambiguous name requires selection; no match and denied access remain distinguishable under the approved disclosure policy.

**Paginated event reads.** Use the canonical customer ID and an opaque continuation token bound to that customer, filter, and snapshot/revision. Define ordering, tie-breaker, page-size limits, token expiry, and whether newly arriving events appear during traversal. The response needs an explicit next token or terminal indication and source/snapshot identity. A consumer must follow every continuation token, detect loops, and preserve the same filter/snapshot. Specify partial failure and retry behavior: a read may be retried only under the same query semantics. Acceptance evidence covers multiple pages, empty collections, repeated/expired token, and source changes during traversal. The final report must identify the snapshot and whether traversal reached its terminal page.

**Export creation.** If export work may outlast the request, return an operation resource with `202 Accepted`, a stable operation ID, and a status/result endpoint. Require an idempotency key scoped to the authenticated principal and equivalent request body; define key retention, conflict behavior for changed bodies, and the meaning of replay. A timeout after submission is an unknown-effect state, not proof that no export exists. The consumer first queries by operation or idempotency key, reconciles status, and only submits again if the API contract proves the original operation was not accepted. The operation states should distinguish queued, running, completed, failed, cancelled, and expired; completed must reference the durable export, its expiry, format, row/count metadata, and access checks. Errors include stable codes, retryability, and whether a side effect may have occurred.

The consumer contract should prohibit reporting completion on request acceptance alone. Completion evidence is a terminal successful operation plus a retrievable artifact whose scope and customer ID match the request. Review server-side object/action authorization on resolution, event retrieval, operation status, and artifact download. Test ambiguous resolution, multi-page traversal, denied access, timeout-after-effect, duplicate idempotency key, changed-body key reuse, and expired artifact. Record any unsupported consistency or recovery guarantee as an explicit gap with an owner; do not claim exactly-once creation from retries alone.
