# Worked example: reconcile approved agents with running deployments

An agent register is useful when a reviewer can resolve discrepancies between the approved inventory and the running estate. Start with a bounded review population and observation window. Join stable deployment identifiers, consuming agents and principals. Record where the join is uncertain. Use the existing [capability admission record](../templates/capability-admission-record.md) and [earned autonomy decision](../templates/earned-autonomy-decision.md) for the authority decision. Runtime observations and containment receipts come from agent-production-operations.

## Scope and evidence

This synthetic example reviews a purchase-order workflow in one production tenant at 10:00 UTC. Policy for this tenant requires a runtime observation within 24 hours for this review. Repeat discovery across the deployment registry, identity provider, enforcement logs, gateway and scheduled work. Record each source's owner, observation time, tenant scope and known blind spots. The registry describes intended deployments. The grant and its activation receipt describe approved scope. Gateway and runtime signals describe observed identity, actions and enforcement. Match using attested deployment identifiers or scoped runtime evidence. A name match or common principal can suggest a join without proving one.

| Agent and deployment | Approved scope and owner | Observed runtime evidence | Authority assessment | Closure owner and required evidence |
|---|---|---|---|---|
| Agent A, deployment D-01 | Grant G-01 permits reads in this tenant. Service owner Asha and approver Emil. | Deployment and gateway evidence from 09:55 link D-01 to principal P-read and show read calls. Current policy denies writes. | Approved and observed scope align for the reviewed tenant. | Asha records the next review date and rechecks after a material policy or deployment change. |
| Unknown agent, deployment D-02 | No matching admission or grant. Human sponsor unknown. | Gateway at 09:56 reports D-02 using P-read, the same principal as D-01. An attested runtime ID identifies D-02. It made a read request that was accepted. | Read access is observed. Approved authority is unestablished. Attribution of older P-read calls without deployment evidence remains unknown. | Runtime owner Jules locates the deployment owner, maps the identity binding, and obtains evidence that the unknown deployment can no longer use the shared principal or has its own approved grant. Review shared-principal impact before disrupting D-01. |
| Agent C, deployment D-03 | Grant G-03 is read only. Sponsor Lin left the team. | Last runtime observation was 48 hours before the review. No current enforcement result. | Approved scope is known. Current deployment status and effective authority are unknown. | Governance owner Priya obtains fresh runtime and enforcement evidence and records an accountable successor sponsor. Record a hold on expansion pending that evidence. |
| Agent D, deployment D-04 | Grant G-04 was suspended at 09:30 by the approved service owner. | Identity receipt shows new authentication is disabled. Queue inspection at 09:58 shows a pending external write created before suspension. The downstream receipt is missing. | New authentication disablement is observed. The effect of the queued write and whether execution is fully contained are unknown. | Runtime owner Jules uses the approved revocation and reconciliation paths. Attach evidence for worker admission and credentials, then a cancellation receipt or an independently observed external outcome with a reconciliation disposition. Escalate if the effect remains unknown. |

Record a restriction, hold, or other decision for each discrepancy with a responsible person and next review trigger. During non-mutating discovery, an unknown principal or stale row is an evidence gap. Route any consequential containment action to the accountable human and the runtime control plan. Link runtime evidence by reference and protect sensitive identifiers and records.

This example treats identity disablement and external-effect reconciliation as separate closure criteria. Review existing sessions, subscriptions, scheduled actions and pending operations where they can still execute. Group deployments by shared identity, model, tool or controller to expose common dependencies and avoid assuming that a single control affects each deployment identically. Scope the register to the available evidence and preserve unresolved discovery coverage.
